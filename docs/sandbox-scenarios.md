# サンドボックス体験シナリオ

`sandbox.html` で、タスク・通知の統制（[設計](./design/voice-task-orchestration.md)）を体験するためのシナリオ集である。
各シナリオは **モック Live** での挙動を前提に書いている。Gemini Live での違いは末尾にまとめる。

---

## 準備

```bash
cd nuage-home
npm run dev
# http://localhost:5173/sandbox.html を開く（音声モードは http://localhost:5173/）
```

設定は `packages/backend/.env` と `packages/frontend/.env` に置く。項目はそれぞれの `.env.example` を参照する。既定値は持たないため、足りない項目があると起動時にエラーになる。

使う部品は画面上部で選ぶ。選択はブラウザに保存され、変えると新しい Live セッションで接続し直す（タスクと通知は残る）。

| 項目 | 選択肢 | 既定 |
| :-- | :-- | :-- |
| Live | モック / Gemini Live（テキスト） | モック |
| LLM | モック（簡易要約） / LiteLLM | モック |
| ツール | モック固定（外部 API や実デバイスを呼ばない） | - |
| ツールの処理時間 | 3 / 8 / 15 / 30 秒 | 8 秒 |

既定ではすべてモックで動き、外部サービスには接続しない。

**リセット**ボタンは、タスク・通知・会話を消し、新しい Live セッションで接続し直す。実行中のタスクは中止され、その結果は通知されない。シナリオごとにリセットしてから始めると、前のシナリオの通知が混ざらない。

### 画面の見方

| 場所 | 見るもの |
| :-- | :-- |
| 発言権 | `待機` / `あなたが発話中` / `応答待ち` / `アシスタントが発話中` |
| タスク | 受付 → 実行中 → 完了・失敗・取り消し。完了すると要約と全文が付く |
| 通知 | 配送待ち → 相乗り中 / 読み上げ中 → 伝達済み。遮られたら `中断（画面のみ）` |
| Live に送った内容 | `ユーザー発話` / `文脈（応答させない）` / `読み上げ指示` / `ツール呼び出し` / `ツール応答` |

### 操作と意味

| 操作 | 意味 |
| :-- | :-- |
| 入力欄に文字を打ち始める | 話し始めた（アシスタントが話していれば遮る） |
| 入力欄を空にする | 発話の取り消し（ノイズ扱い） |
| Enter / 送信 / シナリオボタン | 話し終えた |
| 読み上げ速度スライダー | アシスタントの発話の長さ。遅くすると遮る操作がしやすい |

### タイミングの目安

| 値 | 意味 |
| :-- | :-- |
| 2.5 秒 | 誰も話さなくなってから、通知を読み上げてよくなるまでの猶予 |
| 0.8 秒 | urgent 通知の猶予 |
| 10 秒 | 最後の活動からこの時間内は「会話中」とみなし、通知を相乗りにする |
| 8 秒 | モック autopilot の処理時間 |

---

## S1. 頼んで待つ

**ストーリー**: 用事を頼んで、あとは黙って待つ。終わったら教えてもらえる。

1. シナリオボタン「autopilot で止まってる PR 調べて」を押す。
2. 何もせずに 20 秒ほど待つ。

**確認すること**

- [ ] Live に `ツール呼び出し add_task` が送られ、すぐに `ツール応答 {"status":"accepted"…}` が返る
- [ ] 会話欄に `（無言のターン）` が出た後、「了解、調べておくね。」と相槌が出る
- [ ] タスクが `実行中` になる
- [ ] 約 8 秒後にタスクが `完了` になり、通知が `相乗り中` になる（相槌からまだ 10 秒経っていないため）
- [ ] 最後の活動から 10 秒経つと `読み上げ指示` が送られ、「お待たせ。PR は e2e テストのタイムアウトで…」と話す
- [ ] 通知が `読み上げ中` → `伝達済み` になる

**補足**: ツールの処理時間を 15 秒にすると、会話が途切れた後に完了するため、相乗りを経ずに猶予 2.5 秒で読み上げる流れを見られる。

---

## S2. 雑談中に結果が届く（相乗り）

**ストーリー**: 用事を頼んだ後、別の話をしていたら、話の切れ目で自然に結果を教えてくれる。

1. 「autopilot で止まってる PR 調べて」を押す。
2. 相槌が終わったら、すぐに「週末に京都へ行くんだけど、紅葉のおすすめある？」を押す。
3. 通知が `相乗り中` になるのを待つ（依頼から約 8 秒）。
4. 「嵐山ならお昼ご飯はどこがいい？」を押す。

**確認すること**

- [ ] 手順 3 で、Live に `文脈（応答させない） [相乗り通知] …` が送られ、アシスタントは話さない
- [ ] 手順 4 の応答が「嵐山なら湯豆腐のお店が人気だよ。ところで、PR は…」となる（質問に答えてから触れる）
- [ ] 手順 4 を送った時点で通知が `伝達済み` になる
- [ ] 続けて「ありがとう」と送っても、結果を繰り返さない

---

## S3. 話している間は割り込まない

**ストーリー**: 自分が話している最中に、緊急の通知が来ても遮られない。

1. 入力欄に「えーっと、今日の予定なんだけど」と打ち、**送信せずにそのまま**にする（発言権が `あなたが発話中` になる）。
2. 通知パネルの `urgent` を押す。
3. 10 秒ほど待つ。
4. 入力欄を空にする（発話の取り消し）。

**確認すること**

- [ ] 手順 2〜3 の間、通知は `配送待ち` のままで、何も読み上げない
- [ ] 手順 4 の後、約 0.8 秒で「お待たせ。監視アラート。家のサーバーのディスクが残り少ない。」と話す

**応用**: 手順 2 で `normal` を押すと、発話中は「会話中」とみなされるため `相乗り中` になる。そのまま送信すると、応答の後に「ところで」で触れる。

---

## S4. 読み上げを遮る

**ストーリー**: 通知の読み上げ中に話しかけたら、すぐ黙る。遮った通知は後で画面で確認できる。

1. 読み上げ速度を 4 字/秒に下げる。
2. 何もせず 10 秒以上待ち、会話を途切れさせる。
3. 通知パネルの `normal` を押す。
4. すぐに「お待たせ。洗濯が終わった。」の表示が始まる（猶予の 2.5 秒は既に過ぎている）。表示の途中で入力欄に文字を打ち始める。

**確認すること**

- [ ] 表示が止まり、吹き出しに「…（遮られた）」が付く
- [ ] 通知が `中断（画面のみ）` になる
- [ ] その後しばらく待っても、同じ通知を読み上げ直さない

---

## S5. 進み具合を聞く・取り消す

**ストーリー**: 頼んだことの状況を聞いたり、やっぱりやめたりできる。

1. 「autopilot で止まってる PR 調べて」を押す。
2. 相槌の後、すぐに「さっき頼んだの、どうなった？」を押す。
3. 続けて「やっぱりやめて」を押す。
4. 10 秒ほど待つ。

**確認すること**

- [ ] 手順 2 で `ツール呼び出し task_status` が送られ、「「autopilot で止まってる PR 調べて」は実行中。」と答える
- [ ] 手順 3 で `ツール呼び出し cancel_task` が送られ、「わかった、取り消したよ。」と答える
- [ ] タスクが `取り消し` になり、手順 4 の後も結果の通知が来ない
- [ ] ツール応答に `t-1` のような ID が含まれていない（音声で読み上げさせないため）

---

## S6. 頼んだ作業が失敗する

**ストーリー**: 失敗したときも、成功と同じように知らせてくれる。

1. 入力欄に「autopilot のエラーを調べて」と入力して送信する。
2. 20 秒ほど待つ。

**確認すること**

- [ ] 約 8 秒後にタスクが `失敗` になる
- [ ] S1 と同じ流れ（相乗り → 会話が途切れたら読み上げ）で、「お待たせ。頼まれていた作業は失敗した。autopilot に接続できなかった。」と知らせる

---

## S7. 通知が重なる・文脈だけの通知

**ストーリー**: いくつも結果が溜まったら、1 回にまとめて手短に伝えてくれる。どうでもよい通知は話さない。

1. 「autopilot で止まってる PR 調べて」を押す。
2. 相槌が終わったら、すぐに「autopilot の状況を確認して」を押す。
3. 何もせずに 20 秒ほど待つ。
4. 会話が途切れた後、通知パネルの `low` を押す。

**確認すること**

- [ ] 2 つのタスクが順に `完了` になり、どちらの通知も `相乗り中` になる
- [ ] 最後の相槌から 10 秒経つと、1 回の読み上げで「お待たせ。2件ある。(1) PR は… (2) 自分の番になっているカードが…」とまとめて話す
- [ ] 手順 4 の `low` は `文脈（応答させない）` として送られ、すぐ `伝達済み` になり、話さない

**補足**: 読み上げ待ちが複数あるときに urgent を先にする並び順は、単体テスト（`notification-queue.test.ts`）で確認している。画面の手動ボタンでは、urgent と normal が同時に読み上げ待ちになる状況を作りにくい。

---

## S8. ページを開き直しても結果を失わない

**ストーリー**: 画面を閉じたり接続が切れたりしても、頼んだ作業の結果は届く。

1. 「autopilot で止まってる PR 調べて」を押す。
2. 相槌の後、すぐにページを再読み込みする。
3. 20 秒ほど待つ。

**確認すること**

- [ ] 再読み込み後もタスク一覧に依頼が残っている
- [ ] 約 8 秒後に完了し、新しい接続で読み上げられる

**補足**: タスクと通知は backend プロセスに 1 つだけ保持している。backend を再起動すると消える（永続化は後回しにしている）。

---

## S9. 家電を操作する（フロアライト・カーテン・電球グループ）

**ストーリー**: 照明やカーテンなどの家電操作を頼み、完了通知を受け取る。

1. シナリオボタン「フロアライトをつけて」を押す（または「カーテンを開けて」「電球グループを消して」）。
2. 何もせずに待つ。

**確認すること**

- [ ] Live に `ツール呼び出し add_task {"app":"smart_home","instruction":"フロアライトをつけて"}` が送られ、すぐに `ツール応答` が返る
- [ ] 会話欄に「了解、やっておくね。」と相槌が出る
- [ ] タスク一覧に `smart_home` のタスクが追加され `実行中` になる
- [ ] 約 8 秒後に完了し、読み上げ指示「お待たせ。フロアライトおよびテープライトの点灯を行った…」と結果が伝えられる

---

## S10. 詳しい調査を頼む（Web 検索）

**ストーリー**: Web 検索を用いた詳細な情報調査を依頼し、結果をまとめて報告してもらう。

1. シナリオボタン「京都の紅葉の状況を詳しく調べて」を押す。
2. 何もせずに待つ。

**確認すること**

- [ ] Live に `ツール呼び出し add_task {"app":"research","instruction":"京都の紅葉の状況を詳しく調べて"}` が送られる
- [ ] 約 8 秒後に完了し、「お待たせ。京都の紅葉の調査結果をまとめた。東福寺や永観堂は…」と読み上げられる

## Gemini Live モードでの違い

画面上部の Live を「Gemini Live（テキスト）」に切り替えると、同じシナリオを本物の Gemini で試せる。LiteLLM（`litellm.wpcapp.net`）に接続できる必要がある。

| 観点 | モック | Gemini Live |
| :-- | :-- | :-- |
| ツールの振り分け | キーワード一致（アプリ名・PR・Issue 等と「調べ・確認・見て」等の組み合わせ） | モデルが判断する。自由な言い回しでよい |
| 相槌・応答の文面 | 固定 | 毎回変わる |
| 1 ターンの長さ | 短い | 音声をほぼ実時間で送るため、長い回答では `応答待ち` が 10〜20 秒続く |
| 要約 | LLM の選択に従う | 同じ |
| low 通知 | 使われない | 後で関連する質問をすると、回答に使うことがある |
| 既知の問題 | なし | まれに、応答が 1 ターン遅れて次の発話で押し出される（設計 12 章） |

Gemini モードで試すとよい自由会話の例:

- 「開発の方で、今自分がやらなきゃいけないことある？」（`add_task` が呼ばれるか）
- 「さっきの調べもの、終わった？」（`task_status` が呼ばれるか）
- 結果が相乗りになった後に「ところで何か言いたいことある？」（通知に触れるか）
