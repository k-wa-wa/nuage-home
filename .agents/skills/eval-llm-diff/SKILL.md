# LLM E2E 出力評価スキル (eval-llm-diff)

このスキルは、`nuage-home` において LLM の想定出力（モックデータ / Golden）と実際の LLM 実行出力の差分（Diff）を検証し、エージェント自身（Antigravity や Claude Code）が客観的な Judge として評価・レビューおよびプロンプト改善を行うためのガイドラインである。

---

## 1. 実行手順

### Step 1: テストの実行
評価対象に応じて以下のコマンドを実行する。

```bash
# 全シナリオの Diff を出力
npm run eval:diff

# 特定のシナリオのみ実行（例: lights, kyoto, autopilot）
npm run eval:diff -- --scenario=<keyword>
```

### Step 2: レポートの読み込み
テスト実行完了後、生成された `packages/backend/eval-report.md` を読み込む。
各シナリオごとに以下が記載されている：
- ユーザー発話（User Turn）
- ツール呼び出し結果（Expected vs Actual）
- 評価基準（Criteria: 言葉遣い、正確性、禁止事項）
- 音声メッセージの差分（Speech Diff）
- 詳細レポートの差分（Report Diff）

---

## 2. 評価ルーブリック (Judge Criteria)

各シナリオを以下の 3 つの観点で精査し、それぞれ 1〜5 点で採点する。

| 評価軸 | 観点 | 採点基準 |
| :--- | :--- | :--- |
| **1. Action (動作)** | ツール選定とタスク実行 | **5**: 適切なツール（`add_task`）とアプリが選ばれ、正常に完了している。<br/>**1〜2**: 誤ったアプリが選ばれた、またはタスクがエラー/未完了。 |
| **2. Tone (言葉遣い)** | 音声アシスタント適性 | **5**: 礼儀正しく親切な丁寧語（です・ます調）で統一され、1〜2文（目安60〜80字以内）で簡潔。URLや生ID・記号の読み上げがない。<br/>**3**: 丁寧語だが文が長すぎる、または不自然。<br/>**1〜2**: 常体（〜したよ等）やぶっきらぼうな表現が混入している、または記号や生IDを読み上げている。 |
| **3. Semantic (意味)** | 想定出力との一致度 | **5**: 想定出力（Expected）と本質的な事実・状態・重要提案が一致している。<br/>**3**: 些細な情報抜けがあるが致命的ではない。<br/>**1〜2**: 事実誤認、大きな内容乖離、ハルシネーションがある。 |

### 総合判定
- **✅ PASS**: 全項目が 4 点以上
- **⚠️ WARN**: いずれかの項目が 3 点（改善の余地あり）
- **❌ FAIL**: いずれかの項目が 2 点以下（トーン崩れや動作不良など）

---

## 3. レビュー出力フォーマット

評価結果は以下の形式でユーザーに報告する：

```markdown
### 📊 評価サマリー

| シナリオ | 判定 | 動作 | 言葉遣い | 内容一致 | 要約 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| 家電操作: 照明消灯 | ❌ FAIL | 5/5 | 2/5 | 5/5 | 敬体（〜消しました）の混入 |

---

### 🔍 シナリオ別レビュー: [シナリオ名]
- **判定**: **[PASS | WARN | FAIL]** (動作: X/5, 言葉遣い: Y/5, 内容: Z/5)
- **差分の要約**: 想定出力と実出力の差分の概要
- **講評**:
  - 良かった点
  - 減点理由（特に言葉遣いや不要な情報など）

### 🛠️ 改善提案（プロンプト・コード修正）
減点があった場合、対象ファイル（例: `packages/backend/src/agents/.../agent.ts`）のプロンプト修正案を具体的に diff 形式で提示する。
```
